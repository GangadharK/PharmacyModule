## 1. What this unit delivers

Two tables and the service that is the only thing allowed to write them:

- `inventory_batch` — a quantity of one product, from one supplier, with one
  expiry date. The unit FEFO actually allocates from.
- `stock_transaction` — an append-only ledger of every quantity change, signed.

Plus the API to create and edit batches, quarantine and release them, adjust
stock with a ledger row, and reconcile.

**This unit does not allocate.** FEFO is Unit 06. What lands here is the storage
and the invariant that makes Unit 06 safe: no quantity changes without a ledger
row, and no negative stock.

## 2. The invariant this unit exists to protect

> `SUM(stock_transaction.quantity_changed) GROUP BY batch_id`
> `== inventory_batch.quantity_available` — for every batch, always.

Two things enforce it, and they are independent on purpose:

1. **A database `CHECK (quantity_available >= 0)`.** A concurrent deduction that
   would go negative fails at the database, not in application logic.
2. **A conditional `UPDATE … WHERE quantity_available >= :n`.** Two transactions
   both reading 5 and both trying to take 5: the second matches zero rows and is
   rolled back. This is what makes dispensing safe *without* holding a
   pessimistic lock on every batch.

Neither replaces the ledger. The `CHECK` stops negative stock; the conditional
update stops overselling; only the ledger explains *why* the number moved. A
number with no ledger row is a bug that is invisible until reconciliation.

## 3. Schema

Authoritative in `MDD.md` §3.5–3.6; this is the PostgreSQL 16 translation.

### 3.1 `inventory_batch`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | generated by the application — AGENTS forbids `GenerationType.UUID` so a ledger row can reference the batch in the same transaction |
| `medicine_id` | `uuid` FK → `medicine_catalogue` | nullable; exactly one of this and `item_id` |
| `item_id` | `uuid` FK → `non_medical_item` | nullable |
| `supplier_id` | `uuid` FK → `supplier` | nullable — stock may be received without a supplier recorded |
| `batch_number` | `varchar(100)` NOT NULL | not unique: the same batch number from two suppliers is not a conflict, and the same number for a different product is not either |
| `manufacturing_date` | `date` | nullable |
| `expiry_date` | `date` NOT NULL | the column FEFO sorts on |
| `quantity_received` | `int` NOT NULL | cumulative, never decreases |
| `quantity_available` | `int` NOT NULL | the balance FEFO reads |
| `cost_price` | `numeric(10,2)` NOT NULL | never sent to a `CASHIER` — §5 |
| `selling_price` | `numeric(10,2)` NOT NULL | |
| `location` | `varchar(30)` NOT NULL | `MAIN_PHARMACY`, `OPD_COUNTER`, `EMERGENCY`, `ICU` |
| `status` | `varchar(20)` NOT NULL | `ACTIVE`, `QUARANTINED`, `EXPIRED`, `DEPLETED` |
| `created_at`, `updated_at` | `timestamp(3)` NOT NULL | set by the service, no trigger |

`CHECK` constraints, all in the migration:

- `chk_batch_qty` — `quantity_available >= 0`
- `chk_batch_qty_received` — `quantity_received >= 0`
- `chk_batch_polymorphic` — exactly one of `medicine_id` / `item_id`
- `chk_batch_status` — the four statuses
- `chk_batch_location` — the four locations
- `chk_batch_expiry` — `expiry_date >= manufacturing_date` when manufacturing
  date is present. A batch that expired before it was made is a data-entry error,
  and it would otherwise sort first under FEFO and be dispensed immediately.

### 3.2 The FEFO index is partial

```sql
CREATE INDEX idx_fefo_search ON inventory_batch (medicine_id, expiry_date ASC)
    WHERE status = 'ACTIVE' AND quantity_available > 0;
```

MySQL could not express this, so the MySQL-era plan used a plain composite index
and filtered `status = 'ACTIVE' AND quantity_available > 0` as a residual
predicate — depleted and quarantined rows were physically interleaved with live
ones and the scan filtered row by row. Here the index holds only rows that can
actually be dispensed, so Unit 06's FEFO loop is one range scan in ascending
expiry order with no filter and no in-memory sort.

`location` is deliberately **not** in the index: FEFO filters on it but does not
order by it, so including it would widen the key without helping the ordering.

The mirrored index `idx_item_fefo` exists for non-medical items.

### 3.3 `stock_transaction`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | application-generated |
| `batch_id` | `uuid` FK → `inventory_batch` | |
| `transaction_type` | `varchar(30)` NOT NULL | the ten types in MDD §3.6 |
| `quantity_changed` | `int` NOT NULL | **signed**: `+` in, `-` out |
| `reference_type` | `varchar(30)` | `PURCHASE_ORDER`, `INVOICE`, `RETURN`, `CYCLE_COUNT` |
| `reference_id` | `uuid` | |
| `note` | `varchar(500)` | |
| `performed_by` | `uuid` FK → `users` | **nullable** — null means a system action, i.e. the expiry sweep |
| `created_at` | `timestamp(3)` NOT NULL | |

`quantity_changed` is signed rather than an unsigned magnitude. That single
choice is what makes reconciliation a one-line `SUM`, and it is why every
consumer must not re-derive direction from the type enum.

`performed_by` is nullable on purpose and *only* for the sweep. `CurrentUserContext`
rejects rather than defaults when there is no caller, so a human action can never
be written anonymously by accident.

Indexes: `(batch_id, created_at)` for a batch's history, `(reference_type, reference_id)`
for tracing a purchase order's lines, `(created_at)` for the date sweep.

## 4. Service

`InventoryBatchService`, the only writer.

| Method | Rule |
|---|---|
| `list` | filter by `medicineId`/`itemId`/`supplierId`, `status`, `location`, `expiringBefore`; searchable by `batchNumber` |
| `get` | one batch, 404 via `ResourceNotFoundException` |
| `create` | validates the polymorphic pair, requires `expiryDate`, writes the opening `PURCHASE_IN` ledger row **in the same transaction** |
| `update` | `expiryDate`, `costPrice`, `sellingPrice`, `location`, `supplierId`, `batchNumber`, `manufacturingDate`. **Not** `quantity*` — quantities move only through `adjust` or FEFO |
| `quarantine` | `ACTIVE` → `QUARANTINED`, writes a `QUARANTINE` ledger row with delta `0` |
| `release` | `QUARANTINED` → `ACTIVE`, writes a `RELEASE` row with delta `0` |
| `adjust` | signed delta, ledger row, `DEPLETED` when the balance reaches 0 |
| `expireDue` | marks `ACTIVE`/`QUARANTINED` batches past their expiry date as `EXPIRED` and writes one `EXPIRY_WRITE_OFF` row per batch, zeroing availability. Delta `0` — see §4.2 |

### 4.1 Why quarantine and release write a ledger row with a zero delta

The ledger is the audit trail of *state*, not only of quantity. A zero-delta row
is how "this batch was quarantined on the 3rd, by whom, and released on the 7th"
becomes answerable. A ledger that only records quantity would answer it with a
gap, and a gap is indistinguishable from "it was never quarantined".

### 4.2 Why the expiry sweep does not create a negative movement

`EXPIRY_WRITE_OFF` writes delta `0` and sets `quantity_available = 0`. The stock
is not returned to anyone and the batch is not deleted; it simply stops being
available. Writing a negative delta equal to the remaining balance would also
reconcile, but it would imply the stock left through a process, and the
`EXPIRED` status already says what happened. `status` is the record; the delta is
the arithmetic.

This is the one place `performed_by` is `null`.

### 4.3 `DEPLETED` is derived, never requested

Set by the service when the balance reaches 0. A client cannot set it, and an
update cannot clear it while the balance is 0 — otherwise the row reappears in
FEFO candidate queries as a zero-quantity active batch.

### 4.4 Reconciliation

`GET /api/v1/inventory/reconciliation` returns one row per batch whose
`SUM(quantity_changed)` disagrees with `quantity_available`. An empty result is
the healthy state. It is exposed as an endpoint rather than only a test because
an accountant asking "does the ledger agree?" should not need a shell.

## 5. Cost-price redaction

`cost_price` is the first field in this system a `CASHIER` must not see. AGENTS
rule 7: the field must be **absent from the response body**, not null, and not
hidden by the UI.

`InventoryBatchResponse` carries `BigDecimal costPrice` annotated
`@JsonInclude(NON_NULL)`. The mapper passes `null` when the caller's role is
`CASHIER`, and Jackson omits the key entirely. One record type, one shape in
OpenAPI, and no client can tell the difference between "redacted" and "absent" —
which is correct, because there is no difference to protect.

`selling_price` is **not** redacted: a cashier must be able to read a price to
quote it.

## 7. Expiry sweep

`ExpirySweepJob`, `@Scheduled`, daily. Finds `ACTIVE` and `QUARANTINED` batches
with `expiry_date < today`, marks each `EXPIRED`, zeroes availability, and writes
one `EXPIRY_WRITE_OFF` row with `performed_by = NULL`.

Disabled by default in the `dev` profile behind `app.inventory.sweep.enabled`, so
running the app locally does not silently mutate stock while you are testing.
The sweep is a real ledger writer and therefore runs on its own transaction per
batch, so one poisoned row cannot roll back a day of expiries.

## 8. Verify

- `./mvnw test` — the full suite, with `InventoryBatchServiceTest` and
  `LedgerReconciliationTest` added.
- The ledger invariant is tested against **real PostgreSQL** through the real
  service, not a mocked `EntityManager`. This is the same lesson as
  `ActiveOnlyFilterTest`: a mock accepts whatever it is handed and never
  reconciles, so an inverted delta passes every unit test in the file.
- Boot with `ddl-auto: validate` — a wrong column type stops the app rather than
  corrupting quantities later.
- Live: create a batch, adjust it up and down, read the ledger, reconcile, and
  confirm the sum equals the balance.
